## Two scopes, not one

OSSPlay has two independent permission scopes, designed this way from before any auth code existed:

- **Instance** — the whole self-hosted deployment: one Postgres database, one Docker Compose stack.
  A user either is the instance **root** or isn't; there's no partial instance-level role.
- **Organization** — scoped to one org via membership. Three roles: **owner**, **admin**, **member**.

A third, project-level scope doesn't exist — nothing in the product currently needs per-project access
distinct from org membership.

## Instance root

Root has **implicit full access to everything**, including every organization, with no per-org
membership row required. Concretely, root can:

| Permission | Covers |
| --- | --- |
| `instance:manage_orgs` | Create organizations (including the required onboarding step) |
| `instance:manage_settings` | SMTP configuration, the custom domain and certificate provider |
| `instance:manage_users` | Every account on the instance: force-reset a password, clear 2FA/passkeys, block/unblock, delete, and edit an account's role in any organization |
| `instance:manage_workers` | SSH keys, remote servers, and worker-fleet provisioning |
| `instance:view_audit_log` | Read-only access to the [audit log](/guides/audit-logs) and [error logs](/guides/error-logs) |

`instance:manage_users` is deliberately **not** extended to org owners/admins — a user's password,
2FA secret, and passkeys aren't associated with any particular organization at all, so there's no
existing mechanism for an org-scoped role to reach them. It's root's usual "sees everything" reach
applied to one more resource, not a new kind of scope-crossing. See
[Managing instance users](/guides/instance-users) for what each of these looks like in the dashboard.

## Organization roles

| Role | Can do |
| --- | --- |
| **Owner** | Everything below, plus org settings, deleting the org, and [S3 destinations](/guides/s3-destinations) (`org:manage_settings` — credential-bearing, so it stays owner-only rather than extending to admin) |
| **Admin** | Create/manage/delete [projects](/guides/projects), and manage rules and assets — not membership, org settings, or destinations |
| **Member** | Work within existing projects per their rules |

Root automatically has owner-level access to every organization without needing a membership row —
any permission check scoped to an org short-circuits to "allowed" for root before it even looks at
membership.

## How it's enforced

Permissions are **named bundles resolved from a role**, not individual role checks scattered through
the code (`if (role === 'owner' || role === 'admin')` never appears at a call site) — a request asks
"can this user do `org:manage_members`?" and gets a yes/no, the same shape regardless of which role
ends up granting it. This gets most of the practical benefit of attribute-based access control
(checking a capability, not a role identity) without the cost of an actual policy engine, which isn't
warranted at this project's scale.
